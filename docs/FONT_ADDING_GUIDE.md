# フォント追加・解析の運用手引き

## 情報の分離

フォントを追加するときは、次の3つを別の情報として扱います。

- **フォントの表示利用**: ブラウザやOSで実際に見本を表示するためのCSS指定、配信元、フォールバックなどの設定です。
- **文字収録情報**: フォントの`cmap`を解析し、どのUnicode文字を持つかを確認する情報です。
- **OpenType機能**: GSUB/GPOSのFeatureListを解析し、字形置換や字間調整などの機能タグを確認する情報です。

OpenType機能を確認できても、その機能がブラウザで常に有効になること、すべての文字で効果が出ること、現在の見本で差が見えることまでは保証しません。

## フォントファミリー、個別フェイス、Weight、Style

カード見出しで表示するフォント名は、原則としてフォントファミリー名です。フォントファミリーは同じ設計を共有する書体群のまとまりであり、個別フェイスは同じファミリー内のWeightとStyleの組み合わせです。たとえばRegular 400 / Normal、Bold 700 / Normal、Regular 400 / Italicは、それぞれ別の個別フェイスであり得ます。Boldは通常、別フォントではなく同じファミリー内のWeight 700として扱います。ファミリー名、Weight、Styleを同じ意味として扱いません。

### CSSの`font-family`とフォールバック

CSSの`font-family`にカンマ区切りで複数の名前を書く場合、それらは同一ファミリーの構成要素ではなく、表示できない場合に順番に試すフォールバック候補です。たとえば`"ＭＳ 明朝", "MS Mincho", serif`は、同じファミリーのWeightやStyleの一覧ではありません。

カード見出しのフォントファミリーと、CSSのフォールバック指定は別の情報として記録します。表示利用元またはCSS指定の欄にはフォールバックを含むCSS指定を書いてよい一方、それを解析したファミリーや個別フェイスの根拠とは混同しません。

### Weightの確認方法と表示方針

Weightは推測で決めず、確認できたフォントファイルまたは信頼できる配信設定を根拠にします。Windowsの実フォントを解析する場合はOS/2テーブルの`usWeightClass`を確認します。この数値がWeightの確認根拠であり、代表例として400はRegular、700はBoldに対応します。同じファミリー内でも300、350、400、600、700、900など複数のWeightがあり得ます。

検証環境で確認できたWeightと、このアプリが実際に読み込むWeightは区別します。システムフォントの結果は確認したWindows環境、OS、フォント版に限ったもので、他OSや別バージョンまで保証しません。Webフォントでは、ファミリー全体で提供されるWeightと、このアプリのCSSが実際に読み込むWeightを区別します。現時点のNoto Sans JPでこのアプリが読み込み確認しているのはRegular 400とBold 700であり、ファミリー全体のWeight一覧を確認した意味ではありません。解析できない場合は一般的なフォント知識から補わず「未確認」とします。

### StyleとItalicの確認方針

StyleはNormal、Italicなどの個別フェイス情報です。専用Italicは、実フォントファイルまたは信頼できる配信情報で確認できた場合だけ記録します。Windows実フォントの解析では、OS/2テーブルの`fsSelection`にあるItalic情報を確認根拠にします。ブラウザがNormal書体を傾けて表示する擬似Italicは、専用Italicフェイスが存在することを示しません。擬似Italicが可能でも専用Italic対応とは表示せず、専用Styleを確認できない場合は「未確認」とします。

## 標準手順

### 1. フォントの種類を決める

対象がシステムフォント、リポジトリ同梱ではない外部配信Webフォント、または将来追加されるその他の配信方式のどれに当たるかを決めます。配信方式によって表示確認と解析元の扱いが異なるためです。既存の方式に当てはまらない場合は、無理に既存処理へ合わせず、必要な確認方法を別途定めます。

### 2. 表示利用の条件を確認する

CSS指定名、フォールバック、対象OSまたは配信元を確認します。必要に応じてライセンスと配布条件も確認し、フォント本体を安易にリポジトリへ追加しません。表示できない環境では、フォールバック表示であることを確認し、実フォントでの見本表示とは区別します。

### 3. 解析元を決めて記録する

解析に使うファイル名またはCSS URL、配信元・取得元、解析日、フォントバージョン、解析方法、確認できなかった項目を記録します。TTC/OTCの場合だけ内部フェイス名も記録します。単体のTTF、OTF、WOFF2には内部フェイス名を記録しません。解析元を特定できない場合は、推測で補わず「未確認」とします。

この工程では、次の順序でFont Family、個別フェイス、Weight、Styleの確認範囲も定めます。

1. カード見出しとして使用するフォントファミリー名を決める。
2. CSSの表示指定とフォールバックを記録する。
3. 解析対象ファイルまたはWebフォントの配信設定を決める。
4. 個別フェイスごとのWeightとStyleを解析または確認する。
5. システムフォントは検証環境、解析日時、ファイル名、TTC/OTCの場合はfaceIndexを記録する。
6. Webフォントは、ファミリー全体の提供情報と、このアプリが実際に読み込むWeight・Styleを区別して記録する。
7. 確認できないWeight・Styleは推測せず未確認にする。
8. `cmap`、OpenType機能、Font Family・Weight・Styleの確認結果をそれぞれ別の情報として記録する。

### 4. cmapを解析する

`cmap`から文字収録情報を解析します。文字収録情報とOpenType機能情報は別々に扱います。解析できない場合は推測で補わず「未確認」とし、「未確認」と「解析した結果、該当情報が0件」を区別して保持します。解析失敗時は既存の生成データを壊さないことを確認します。

### 5. OpenType機能を解析する

GSUBとGPOSのFeatureListから機能タグを抽出します。同じタグが両方にある場合は1件に統合し、GSUB・GPOSの両方に所属することを記録します。画面に表示するのは、解析または信頼できる公式情報で確認できた機能だけです。表示されていない機能を未収録とは断定しません。

新しいタグが出た場合だけ、OpenType公式仕様を根拠に共通説明辞書を追加します。説明を確認できないタグは推測で説明しません。

### 6. データと画面への反映を確認する

フォントごとの個別UIを増やさず、既存の共通カード、OpenType詳細ダイアログ、機能チップを利用します。新しいフォントは解析データとメタ情報を登録すれば既存UIで表示できる構成を維持します。表示利用、文字収録情報、OpenType機能のそれぞれが適切なデータに反映されていることを確認します。

### 6.1 解析サマリーと証拠データを分ける

通常表示に必要な`cmap`の圧縮済み`ranges`、`codepointCount`、解析状態、Weight / Style、ファイル数、版の概要、統合済みOpenType機能一覧は起動時サマリーへ残します。未収録文字の判定と機能チップを表示するだけでは、詳細JSを読み込ませません。

ファイル別URL、SHA-256、ファイルサイズ、`unicode-range`、User-Agent、CSS取得情報、ファイルごとの機能結果などの証拠は、`analysis-details/<font-id>.js`へ1つの`files`配列として正規化します。詳細JSにはフォント本体を入れません。`file://`運用も維持するため、詳細はJSONの`fetch()`ではなく従来型`script`で読み込み、利用者由来の値ではなく許可済みIDと相対パスの対応表を使います。

詳細ダイアログでは起動時サマリーをすぐ表示し、その後に対象フォントの詳細だけを読み込みます。同一画面では成功した詳細をキャッシュし、失敗時は再試行できるようにします。未解析または詳細なしのフォントには読込要求を出しません。再生成時はサマリー2ファイルと対象詳細JSを一時出力・検証してからまとめて置換し、部分更新で他フォントの詳細を削除しません。

### 7. テストとCIを確認する

関連するJavaScriptテスト、Python解析テスト、構文確認、`git diff --check`、GitHub Actions CIを実行・確認します。通常CIではネットワークに依存しないfixtureテストを中心にし、解析失敗時に既存の生成データを壊さないことを確認します。失敗した場合は生成物を更新せず、原因を記録してから修正します。

### 8. README、LOG、解析元一覧を更新する

Markdownは実装・解析・検証の結果を記録するための文書です。未確認の事実や未実行の確認結果を先に固定してしまわないよう、README、`LOG.md`、[解析元一覧](FONT_ANALYSIS_SOURCES.md)、手引きは作業開始時に先に書きません。

まず解析元、バージョン、解析日、未確認理由などの事実を確認します。コードまたはデータを変更する作業では、その変更、テスト、`git diff --check`、GitHub Actions CIの確認を先に終え、確認結果がそろった最後の工程でREADME、`LOG.md`、解析元一覧、手引きを記述・更新します。

Markdown更新後は、リンク、表、見出し、`git diff --check`をもう一度確認します。未実行の確認結果、推測した数値、未確認の情報をMarkdownへ書きません。フォントを追加するPRでは、表示利用の根拠と解析の根拠を同時に更新します。

## Webフォントの運用

現時点では、Noto Sans JPのGoogle Fonts配信版を解析した実装が一例です。Webフォントの配信方法は今後拡張・変更される前提で運用します。

- 現在の実装は、Google Fonts CSSから対象WOFF2 URLを取得し、配信ファイルを解析する方式です。
- CSSの`unicode-range`により複数のWOFF2へ分割されるため、文字収録情報は配信対象ファイルの`cmap`を統合しています。
- この統合は、一回のページ閲覧で全WOFF2が取得されることを意味しません。
- Google FontsのCSS、配信ファイル数、ウェイト、スタイル、バージョン、`unicode-range`は将来変化し得ます。
- 現在のNoto Sans JPの設定は、特定のCSS URL、ユーザーエージェント、ウェイトを対象にした確認結果です。
- 今後は、可変フォント、italic、追加ウェイト、別CDN、Google Fonts以外のWebフォント、自己ホスト型WOFF2などを扱う可能性があります。
- 新しいWebフォントを追加するときは、既存のNoto Sans JP用処理をそのまま流用できるか確認し、配信方式が異なる場合は無理に当てはめません。
- 通常CIはネットワークに依存しないfixtureテストを中心にします。
- 実際の配信内容を確認するライブ解析は手動Actionsで実行し、結果をartifactとして確認します。
- 手動ライブ解析は、workflowファイルがデフォルトブランチに存在してから実行できます。
